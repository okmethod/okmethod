# エンジニアとPMの二人三脚理論

エンジニアリングとプロジェクトマネジメントは、別の専門領域。  
プロジェクトを成功させるためには、エンジニアとPMの双方が専門家として自分の領分に責任を持ち、 **「二人三脚」** で取り組むのが理想。

しかし、PMの関心事を理解しないまま協働しようとしても、的を射た助言も、建設的な分担も生まれない。  
そのため、PMBOK のPM知識エリアをベースとしつつ、各エリアのスタンスを明らかにすることで、「二人三脚の役割分担のイメージ」の擦り合わせを試みる。

注: 本文書は SIer・受託開発におけるウォーターフォール型のコンテキストを主な経験基盤として記述している。自社プロダクト開発や、アジャイルマニフェストの価値観を実践する開発においてはこの限りではない。なお、アジャイルの名称のもとでウォーターフォールの規律を崩した状態は、本文書のコンテキストの範疇とも言いがたく、そもそもアンチパターンと考える。

## 二人三脚とは

**二人三脚**: エンジニアとPMがそれぞれの専門性を持ち寄り、共同でオーナーシップを担うイメージ。  
きっちりと線を引いて「どちらかに任せる」のではなく、「両者が主体的に動き、噛み合わないと機能しない」という強い依存関係・信頼関係を指す。

役割分担を考えるときの軸は **「誰が主導するか」**。

- 技術的判断と密結合 → エンジニアが主導する
- 技術的判断と疎結合 → PMが主導する

**「PMが主導する」は「エンジニアが関与しない」ではない。**  
主導しない領域でも、エンジニアとして果たすべき **インプット責任** がある。

### 二人三脚ではない例（アンチパターン）

このような姿勢は、二人三脚とは言えない。

- **押し付け合い**: 互いに「それはあなたの仕事」と責任を押しつける
- **寄りかかり**: 片方が自分の領分でベストを尽くさず、もう片方に負荷が偏る
- **引きずり**: 片方がペースを乱し、もう片方がそれに合わせることを余儀なくされる
- **分断並走**: 互いに自分の仕事をしているように見えるが協働しておらず、責任の隙間にボールが落ちやすい

特に、「寄りかかりに対する指摘」と「押し付け合い」は一見区別がつかない点に留意が必要。  
そうならないためにも、双方で共通した「二人三脚の役割分担のイメージ」を持つことが重要となる。

## 各エリアのスタンス

### 1. 統合管理 — PM主導領域

プロジェクト計画書全体のオーナーはPM。PMが各項目を整合させ、プロジェクト全体の方針として管理する。  
エンジニアは計画の根拠となる技術的インプット（設計・見積もり・リスク）を提供し、技術的に実現不可能・非現実的な計画に対してはプッシュバックする責任を持つ。

ここで重要な区別がある。  
「**計画**」（いつ・何の基準で・誰が判断するか）のオーナーはPMであり、「**設計**」（どう技術的に実現するか）のオーナーはエンジニアである。  
両者は一方向の「根拠と結果」ではなく、相互制約の関係にある。PMの計画が設計の方向性を規定し（トップダウン）、エンジニアの設計・見積もりが計画の実現可能性を規定する（ボトムアップ）。
この往復によって計画と設計の双方が収束していく。

**プロジェクト計画書の骨子例:**

| 項目                                                   | 主担当 | エンジニアの関与                             |
| ------------------------------------------------------ | ------ | -------------------------------------------- |
| プロジェクトの背景・目的                               | PM     | —                                            |
| プロジェクトのスコープ（やること・やらないこと）       | PM     | 技術的実現可能性・工数のインプット           |
| マスタスケジュール                                     | PM     | ブレイクダウン素案・フィージビリティチェック |
| 予算計画                                               | PM     | 見積もり・インフラコスト提供                 |
| 体制図・役割責任（RACI）                               | PM     | 技術タスクの RACI はエンジニアが原案を出す   |
| コミュニケーション設計（会議体・ファイル授受方法、等） | PM     | —                                            |
| テスト計画（別紙可）                                   | PM     | テスト設計を根拠として提供                   |
| リリース計画・移行計画（別紙可）                       | PM     | リリース設計を根拠として提供                 |
| リスク管理表（別紙可）                                 | PM     | 技術リスクを検知・起票                       |

### 2. スコープ管理 — 共通領域

スコープは **Why（目的・ビジネス要求）→ What（課題・目標）→ How（解決手段・システム要件）** の階層で捉える。

- **Why・What**: PMが主導して定義する。エンジニアはPMが提示する「要望（How）」を鵜呑みにせず、背後にある目的（Why）との整合性を確認・検証する責任を担う。それを踏まえて技術的な代替案を提示することはエンジニアの役割だが、最終的な機能スコープの判断はPMが行う。
- **How（機能スコープ）**: PMがオーナー。エンジニアは技術的実現可能性・工数・技術リスクの観点についてインプットする責任を担う。スコープ変更の技術的影響を可視化する際は、個別の変更影響だけでなく、変更の累積による肥大化（スコープクリープ）もあわせて示す。
- **技術スコープ**（アーキテクチャ・リファクタリング・技術的負債の返済範囲）: エンジニアが主導し、PMと合意形成する。機能スコープと技術スコープは別軸で管理する。「技術スコープ」はPMの共通言語にないため、エンジニアがリスク・コスト・機能への影響という形に翻訳してPMに提示することが合意の前提となる。
- **受け入れ基準**: スコープの定義と対をなすため、スコープ合意と同時に合意する。「仕様通りに動くか」の検証（UAT）は、業務要件定義で定めたユースケース・シナリオをそのまま転用できる。逆説的に、UATにそのまま転用できる業務要件定義を書く必要がある。

Why/What/How間のトレーサビリティを常に確認し、変更要求が発生した際には整合性を保ちながら対応する。

### 3. スケジュール管理 — 共通領域

**「完璧なスケジュール」は幻想:**

「スケジュールは守るもの」というスタンスだと、「最初に完璧なスケジュールを立てられる」という幻想を前提としてしまうリスクがある。
プロジェクトには必ず想定外の出来事が起きる。スケジュールを「固定された正解」として扱うと、遅延を隠蔽したり品質を圧縮して帳尻を合わせようとする歪みが生まれる。  
引き直し（再計画）は失敗の証拠ではない。
常に「最新版スケジュール」を更新し続けることが正常な適応行動であり、正直な状態共有こそが健全なプロジェクト運営の前提となる。

ただし、これは「想定外が起きたから遅れは仕方ない」という姿勢ではない。
このスケジュールが遅れたら、どこの誰に影響があるのか＝マイルストーンを冷静に分解し、誰にも迷惑をかけないラインは柔軟に・誰かに迷惑がかかるラインは厳格に、を使い分ける必要がある。

**計画フェーズ:**

全体スケジュール・マイルストーンの設定はPMが主導する。  
エンジニアはフィージビリティチェックを行い、非現実的な場合は「なぜ無理か」だけでなく「こうすれば現実的になる」という代替案をセットで返す。
その後、開発タスクに関してはPMから依頼された範囲をエンジニアがブレイクダウンし、PMがそれを全体スケジュールに統合・調整する。

PMのマイルストーンとエンジニアのブレイクダウンは、どのタスクがどのマイルストーンに対応するかを明示的に合意することで初めて機能する。
この対応付けが曖昧なまま進むと、「PMは計画通りと思っているが開発は行き詰まっている」「想定外の事態が起きた時のスケジュール修正をスムーズに行えない」という状態が生まれやすい。

また、PMとエンジニアは「どの状態になったらエスカレーションするか」のトリガー条件を事前に合意しておく。
これが不明確だと、エンジニアは過剰報告or報告不足に陥りやすい。

**実行フェーズ:**

遅延が発生した場合、影響の届く先によって対応を使い分ける。

| 遅延の種類         | 具体例                                       | 対応                                                 |
| ------------------ | -------------------------------------------- | ---------------------------------------------------- |
| **外部厳守ライン** | 契約納期・顧客向けデモ・UAT開始日            | 厳格に守る。リスクが見えた時点で即時エスカレーション |
| **内部波及ライン** | PMの報告タイミング・他チームへの成果物引渡し | 影響が出る前にPMへ早期警告 + 再計画を共同で実施      |
| **自己吸収ライン** | チーム内バッファ・クリティカルパス外のタスク | エンジニアが自律的に調整。PMへの都度報告は不要       |

遅延を報告する際は「遅れている」という事実だけでなく、「なぜ・どの程度・どう対処できるか」「どこの誰にどのような影響があるか」をセットで伝えることで、PMが対策を判断できる状態にする。
逆に言えば、「厳格に守る」ラインこそ、技術リスクを踏まえたバッファを明示的に計画すべき対象である。想定内の揺れを内側で吸収できれば、コミットラインを本当の意味で守れる。

### 4. コスト管理 — PM主導領域

予算管理・予実管理のオーナーはPM。  
エンジニアは「費用面（インフラランニングコスト等）」と「稼働工数面」の両軸で、見積もり作成と実績報告を担う。
コストが超過傾向にある場合は受動的に待つのではなく、エンジニアから能動的に可視化・報告する。

エンジニアが精度高く見積もりを出すことが、PMのコスト管理を成立させる前提になっている。  
見積もりは「数字」ではなく「前提・根拠・バッファを伴った数字」として提示することが重要である。
根拠のない数字はPMが検証・説明できず、交渉や意思決定の材料にならない。

**見積もり前提の原則:**

見積もりの粒度は、見積もりの目的（何の意思決定に使うか）で決まる。  
粗すぎると意思決定の根拠にならず、細かすぎると要件がまだ流動的な段階での過剰な作業となり、後の変更で無駄になるリスクがある。

そして、見積もりの精度は依頼の質で決まる。  
以下の「見積もり前提」を整理した上で依頼することはPMの責任範囲であり、これがエンジニアの精度ある見積もりを引き出す前提となる。

| 項目               | 内容                                                                     |
| ------------------ | ------------------------------------------------------------------------ |
| 目的               | 何の意思決定に使うか（提案価格の根拠・予算計画・WBSへの落とし込みなど）  |
| 必要な粒度         | どの粒度が必要か（概算・フェーズ別工数・タスク単位の積み上げなど）       |
| 前提条件・制約条件 | 何が前提・制約となるか（要件の確定度・技術的制約・ビジネス上の制約など） |
| 期限               | いつまでに必要か                                                         |

これらの情報が整理されていない依頼に対して、エンジニアはPMに確認を求めること。  
整理されていない・確認できない段階での見積もりは「前提を仮定した上での見積もり」となり、見積もり自体のコストが高くなること、前提が変われば見積もりも変わる旨をセットで伝える。

**見積もりの原則:**

- **前提・制約の明示と確度の表明**: 何を前提にした見積もりか・どの程度の幅があるかを数字とセットで提示する
- **バッファの根拠化**: リスク・不確実性に応じたバッファを積む。「なんとなく」ではなく、何のリスクに対するバッファかを説明できる状態にする
- **定期的な更新**: 要件変更・設計進展に応じて見直す
- **プレッシャーへのプッシュバック**: 圧縮を求められた場合、根拠を示した上で「この工数が必要な理由」を説明する責任を持つ

### 5. 品質管理 — 共通領域

品質は「サービス品質」と「コード品質・テスト品質」の2軸で捉える。

**サービス品質:**

ユーザーが感じる動作品質。さらに2層に分かれる。

- **明示的サービス品質**: SLA/SLO・性能・可用性・セキュリティなど、定量的に合意できる非機能要件。設計初期にPMと合意するのが原則で、後からの追加・変更は設計の大幅見直しを要する。エンジニアがシステムの特性をもとに候補値を提示し、PMがビジネス要求・コストとのバランスで判断する。
- **暗黙的サービス品質**: 仕様は満たしているが「なんかイケてない」状態 - 操作感・画面遷移・エラー表示の使い勝手など、定量化しにくい定性的な品質。ユーザーが触れて初めて顕在化しやすく、UATで初めて「これじゃない」が起きる典型パターン。ウォーターフォールでは、モックアップ・プロトタイプ・画面遷移設計のレビューを設計フェーズに組み込み、早期に可視化することが対策となる。

なお、「仕様通りに動くかどうか」の二値的な検証は受け入れ基準として「2.スコープ管理」の文脈で扱う。

**コード品質・テスト品質:**

ユーザーには直接見えないが、開発の持続可能性を左右する内部品質。
テスト設計・CI/CDパイプラインによる品質ゲート・コードレビューポリシーなど、品質保証の仕組みそのものはエンジニアが設計・運用する。

この領域はPMの視野に入りにくい。
内部品質の劣化（技術的負債の蓄積）が放置されると、後続フェーズの開発速度低下・障害増加・修正コストの上昇として顕在化する。
エンジニアは「この内部品質の低下が、いつ・どのようなコストとして顕在化するか」を可視化してPMに伝える翻訳責任を担う。

**品質 vs コスト・スケジュールのトレードオフ:**

品質基準を下げる意思決定の主体はPM。
ただしエンジニアは、その判断材料として「品質を下げた場合の技術的コンセクエンス（後から修正する場合のコスト・リスク）」を提示する責任を持つ。
根拠なく妥協することと、リスクを明示した上で判断を委ねることは全く異なる。

なお、QAロールが社内に定義されている場合は品質保証の仕組み設計の主体がQAに移るが、技術的観点のインプット責任はエンジニアが引き続き担う。

### 6. 資源管理 — PM主導領域

**チーム編成・人員調達:**

PMと自社マネジメント層が主導する。  
エンジニアは「必要なスキルセット・人数の情報提供」「キャパシティの超過・不足の申告」「採用面接での技術評価」を通じてPMの判断材料を補う。
特にキャパシティの逼迫は、受動的に待つのではなく早めに申告することが重要。

**育成（メンタリング・スキル開発）:**

エンジニアリングマネージャーの責任領域。  
エンジニアが後進育成に関わる場合は、PJ遂行と兼務させるのではなく、育成自体をスコープとして明示的に合意した上で担う形が望ましい。

### 7. コミュニケーション管理 — PM主導領域

ステークホルダー管理が「誰に何を伝えるか」の戦略・内容であるのに対し、コミュニケーション管理は「どの場・手段・頻度で伝えるか」の仕組み・体制設計。

PMが会議体（社内・社外）の目的・頻度・出席者を定め、各回のアジェンダ作成と進行を担う。  
連絡手段・窓口の設計（Slackチャンネル設計、一次受け担当の明確化など）もPMの責任範囲。
エンジニアはPMからのアジェンダ依頼に応えるだけでなく、自ら議題を提起してアジェンダに追加してもらう形で能動的に関与する。

**会議体の目的分類とエンジニアの関与条件:**

プロジェクトで発生する会議体は目的が異なり、エンジニアに期待される役割も異なる。  
PMはエンジニアを招集する際に、「何のために参加を求めているか（目的・期待役割・事前準備の依頼）」を明示することが前提となる。
これが整わないまま「とりあえず参加」「その場で突然話を振る」という形になると、準備のできていないエンジニアが会議に引き出されるだけとなり、会議の質・エンジニアの作業時間の両方を損なう。  
目的・役割が不明な招集に対して、エンジニアはPMに確認を求めること。  
（顧客が関与する会議については「10.ステークホルダー管理」も参照）

### 8. リスク管理 — 共通領域

リスク管理表はチーム全体で共有するもの。  
表全体のオーナーはPMだが、技術リスクはエンジニアが能動的に発見・起票する責任を持つ。
技術リスクはエンジニアが識別・起票しないとそもそも管理対象に入らず、PMのリスク管理は空洞化する。
起票後の精緻化・担当者としての対応もエンジニアが主体的に担う。

対応方針は一般的に「低減/受容/回避/転嫁」等に分類されるが、PJ文脈ではどの方針を選んでも時間・コスト・スコープのいずれかに影響するため、対応策はいずれも「合意形成」に着地する。
エンジニアの役割は「リスクを処理する」ことよりも、「PMが方針を判断・対応を合意形成できる状態を作る」ことにある。

**技術リスクの分類例:**

エンジニアが識別・起票すべき主な技術リスクのカテゴリ。

| カテゴリ           | 例                                                                       |
| ------------------ | ------------------------------------------------------------------------ |
| 技術的不確実性     | 新技術・未検証アーキテクチャ・スパイク調査が必要な領域                   |
| 外部依存           | 外部API・サードパーティライブラリ・クラウドサービスの仕様変更・廃止(EOL) |
| 要件不確実性       | 要件の確定度が低い・後から変更が想定される領域                           |
| 工数・見積もり     | 見積もり精度が低い・不確実性の高い開発タスク                             |
| セキュリティ・品質 | 既知の脆弱性・技術的負債が顕在化するリスク                               |

**リスク管理表の骨子例:**

| 項目                 | 内容                                                                   |
| -------------------- | ---------------------------------------------------------------------- |
| リスク内容           | 何が・どう起きうるか（原因と結果を一文で）                             |
| カテゴリ             | 上記分類                                                               |
| 発生確率             | 高 / 中 / 低                                                           |
| 影響度               | 高 / 中 / 低（スケジュール・コスト・品質のどれに・どの程度影響するか） |
| 優先度               | 発生確率 × 影響度から算出                                              |
| 対応方針             | 低減 / 受容 / 回避 / 転嫁                                              |
| 対応内容・アクション | 具体的な対応策と担当者                                                 |
| 期限                 | 対応・再評価のデッドライン                                             |
| ステータス           | オープン / 対応中 / クローズ                                           |

影響度「高」のリスクを検知した場合、ステータスが変化した場合（状況悪化・新情報による影響度の上昇）は即時共有するなど、リスク管理表をリスク関連の情報共有・エスカレーションの運用フローの土台にするとよい。

### 9. 調達管理 — PM主導領域

「外部委託 vs 自社開発」の意思決定に必要な情報を出すのがエンジニア、判断・調達のオーナーはPM。
契約形態（請負・準委任・派遣）に応じて役割分担が変わるため、両者の理解が前提となる。

- **請負**:
  - 委託先は「成果物を納品する独立した事業者」。指揮命令は不可。成果物が受け入れ基準を満たさない場合は瑕疵として対応を求めることができる。
  - PM: ベンダー選定・入札・契約を主導する。マイルストーンごとの正式な検収判断と、変更要求発生時の追加費用交渉を担う。
  - エンジニア: 委託先はエンジニアのアンダーには入らない。自社開発部分との技術的I/F・受け入れ基準を定義し、検収時に成果物の技術的品質をレビューする。
- **準委任**:
  - 委託先は「独立した外部専門家」。指揮命令は不可。日常的な業務指示や進捗管理が必要な業務に準委任を選ぶのは契約形態の選択ミスであり、その場合は派遣に切り替えるべき。
  - PM: 業務範囲・報酬・期間の契約交渉を担う。作業報告の受理と、継続・スコープ変更の判断もPMが行う。
  - エンジニア: 委託先はエンジニアのアンダーには入らない。技術的な要件・受け入れ基準の定義と成果物レビューを担い、相手とは対等な協議者として関わる。
- **派遣**:
  - 3形態の中で唯一、指揮命令権がクライアント側に移転する契約。法的な雇用関係は派遣元にある。
  - PM: 派遣元との契約・スキル要件定義・条件交渉を担う。受け入れ期間の延長・終了判断もPMが行う。
  - エンジニア: 外部エンジニアをチームメンバーとして受け入れ、業務指示・進捗管理を直接担う。

### 10. ステークホルダー管理 — PM主導領域

主要ステークホルダーは「顧客（発注者）」「想定ユーザー」「自社マネジメント層」。
最重要は顧客で、提案・報告・要件調整が主な接点となる。

**PMの役割: 期待値管理・顧客窓口**

PMは、誰にどんな情報・ストーリーを渡し、期待値をどう調整し、どの落とし所に持っていくかをリードする。
顧客との接点はPMが主導するのが原則であり、スケジュールや工数の理由説明はPMが代弁できるべき。エンジニアはPMが正確に伝えられるよう十分な情報を渡す責任を持つ。

**エンジニアの直接関与の原則:**

エンジニアが顧客・ユーザーと直接関与することは、本来ベストプラクティスである。  
技術的専門性が求められる場面でのダイレクトなコミュニケーションは、PMを介した情報伝達では損なわれる技術的文脈を保全し、意思決定の質を高める。

ただし、これが日常的に機能するのはアジャイル型開発においてである。
真のアジャイルは探索的であり、スコープと納期を初期段階で固定しないことを構造的な前提とする。
その前提があってこそ、顧客との継続的な直接対話がフィードバックループとして成立する。  
SIer・受託開発のウォーターフォールモデルはスコープと納期を契約で固定するため、この構造が成立しにくく、PMが契約境界を管理することが自然な役割分担となる。

**エンジニアの直接関与を機能させる条件:**

エンジニアの直接関与が機能するには、PMがその場の目的・エンジニアへの期待役割・コンテキストを事前に明示することが前提となる。  
これが整わないまま「とりあえず同席」「その場で突然話を振る」という形になると、PMが担うべき調整・文脈管理がエンジニアに転嫁される構造となり、望ましくない。  
資料作成を依頼する場合も同様に、PMが全体骨子と各コンテンツの目的を明示した上で依頼するのが妥当。

顧客同席の場では特に、この条件が整わないまま進むと、顧客にチームの連携が不十分な印象を与えるリスクがある。  
（招集に際しての一般的な原則については「7.コミュニケーション管理」を参照）

## インターフェース（接続点）の設計

「各々がきっちりやる」だけでは機能しない、明示的な接続点の設計が必要な場面がある。

| 接続点               | PM視点                                                                                                       | エンジニア視点                                                                                                                     |
| -------------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| 見積もり書           | 目的・必要粒度・前提条件を整理した上で依頼する。<br>受け取った見積もりを予算計画・顧客交渉の根拠として使う。 | 前提・根拠・バッファを明示して作成する。<br>前提が不明な依頼には確認を求める。                                                     |
| プロジェクト計画書   | 全体のオーナー。<br>各インプットを統合・整合させ管理する。                                                   | 技術項目（フィージビリティ・タスクブレイクダウン・リスク）を提供する。<br>非現実的な計画にはプッシュバックし代替案をセットで返す。 |
| テスト計画書         | 対外的な品質保証の説明責任を担う。<br>UAT開始条件・受け入れ基準をステークホルダーと合意する。                | テスト設計を根拠として記述する。<br>テストスコープ・体制・実施期間・環境を定義し、プロジェクト計画への組み込みを求める。           |
| リリース計画書       | スケジュール・リソース調整のベースにする。<br>Go/No-Go判断の主体として関与する。                             | リリース設計を根拠として作成する。<br>技術的依存関係・ロールバック条件を明示する。                                                 |
| リスク管理表         | 全体のオーナー。<br>対応方針の判断と合意形成を主導する。                                                     | 技術リスクを能動的に識別・起票する。<br>起票後の精緻化・対応も主体的に担う。                                                       |
| 要件定義書           | Why・Whatを定義し、機能スコープの最終判断を行う。                                                            | Howの技術的実現可能性を検証し、代替案を提示する。<br>UATに転用できる粒度で書かれているかを確認する。                               |
| 会議資料・アジェンダ | 会議体の目的・頻度・出席者を設計する。<br>エンジニア招集時は目的・期待役割・準備依頼を明示する。             | 自ら議題を提起してアジェンダに追加する。<br>目的・役割が不明な招集はPMに確認を求める。                                             |
